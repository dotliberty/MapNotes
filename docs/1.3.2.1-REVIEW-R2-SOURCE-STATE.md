## Исправление

`MapTrace.snapshot()` теперь добавляет к истории **актуальный memory-only снимок** состояний всех источников живых зарегистрированных atlas. Эти строки вычисляются при экспорте из текущих очередей, активных импортов, LRU/disk descriptors и сохранённых enum outcomes. Они не зависят от того, остались ли старые события START/ERROR в кольце, и не требуют нового draw.

- Кольцо по-прежнему содержит максимум **2048** исторических событий. Актуальные строки не занимают его слоты: их **3 на индексированную Area**, отдельно для full/simplified/walls. Число строк определяется текущим каталогом живых atlas, а не количеством прошлых событий. Новые tracking collections содержат только ключи активных импортов и enum outcomes, без исключений или графов геометрии.
- Реестр providers использует weak keys; `close()` явно удаляет provider. Уже закрытый atlas не добавляет строки актуального состояния.
- Общий monitor `MapTrace` отпускается **до** обращения к providers. Providers не берут общий atlas monitor карты/стен, не выполняют file IO/stat, не запускают импорт. Для LRU используется `snapshot()`, а не `get()`: экспорт не меняет recency/hit counters. Disk descriptors читаются из concurrent map без открытия файлов.
- Импорт отмечается до ожидания общего atlas monitor. Поэтому worker, уже приступивший к обработке, различим как IMPORTING даже во время ожидания этого monitor; только поставленный в очередь job остаётся QUEUED.
- Состояния готовности читаются заново. После eviction нет ложного READY. Стены могут использовать готовое полное представление источника так же, как существующий `nearWays`.
- FAILED/MISSING outcomes фиксируются в существующих обработчиках ошибок импорта; чтение файла и попытки повторного импорта сохраняют прежний lifecycle. OOM outcome фиксируется как FAILED без изменения прежней политики retry. Сами ошибки остаются также историческими ERROR/OOM событиями.

Формат строки в том же CSV:

```text
0,nanos,0,SOURCE,STATE,sourceToken,variant,state,sourceRevision
```

`seq=0` означает актуальный снимок, а не историческое событие; `nanos` — время экспорта. Source token — identity Area в процессе, revision — её индексированный stamp. Названия, пути, URI, координаты и заметки не экспортируются.

| Поле | Значения |
|---|---|
| variant | **1 DETAIL** — full-представление файла; **2 OVERVIEW** — simplified `#o` этого же файла; **3 WALLS** — стены |
| state | **1 QUEUED**, **2 IMPORTING**, **3 READY**, **4 MISSING**, **5 FAILED** |

Decode-вариант OVERVIEW `#o` отличается от выбора физического `overview.json.gz` на z12: каждый физический источник имеет свой sourceToken и свои три варианта. MISSING означает, что данных варианта сейчас нет в ready/active/queue: в том числе ещё не запрошенный или вытесненный вариант либо не открывшийся исходный файл (`FileNotFoundException`). Это не доказательство физического удаления файла; filesystem на UI не опрашивается. FAILED обозначает сохранённый неуспешный импорт, например malformed JSON, отдельно от этого отсутствия данных.

## Восстановление после OOM и успешного retry

Следующий review Бобы обнаружил stale outcome: **контролируемый OOM → успешный retry → READY → LRU eviction → FAILED**, хотя после eviction должен быть MISSING. Реального исчерпания JVM heap не было: тестовый File однократно бросает `OutOfMemoryError` во время импорта.

До исправления выполнен **неизменённый** `BobaSourceRecoveryReviewTest` из той же внешней папки tests, плюс две собственные регрессии memory/disk. Все три упали: **3/3 failures**, после потери ready state=**5 FAILED**, ожидался **4 MISSING**. Полные red XML и snapshots сохранены в **`build/review-r2/source-recovery-red/{xml,trace}/`**; результат исходного теста — `TEST-ru.main.explorer.BobaSourceRecoveryReviewTest.xml`.

В `OfflineAtlas.loadSource` добавлено только очищение **`sourceOutcomes.remove(key)` после успешной публикации**: в memory-ветке после успешного `cacheGeometry`, в disk-ветке после `diskGeometry.put`. Key включает суффикс full/`#o`/`#walls`, поэтому очистка не затрагивает outcomes других вариантов и не происходит при неуспешной/отменённой публикации.

После исправления исходный repro проходит: **FAILED → READY → eviction → MISSING (4)**. Обе новые регрессии сначала контролируемо ошибаются на всех трёх вариантах одного источника, затем восстанавливают их по одному. После снятия ready и переполнения кольца:

| Успешно восстановленный вариант | full / simplified / walls |
|---|---|
| full | **MISSING / FAILED / FAILED** |
| затем simplified | **MISSING / MISSING / FAILED** |
| затем walls | **MISSING / MISSING / MISSING** |

Для memory применяется настоящий `LruCache.evictAll`. Disk descriptor не участвует в LRU: в отдельной fixture явно снимается и закрывается только его тестовый ready entry. Это проверка очистки outcome disk-веткой, а не утверждение о существующем disk LRU eviction. Исходные файлы не удаляются. Снимки каждого шага: `recovery-memory-variant-{1,2,3}.txt` и `recovery-disk-variant-{1,2,3}.txt`.

Полный green — **`build/review-r2/source-recovery-green/{xml,trace}/`**, включая исходный XML Бобы и его `boba-successful-retry-then-eviction.txt`.
